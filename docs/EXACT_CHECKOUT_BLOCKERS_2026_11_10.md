Check status instead of submitting again.` No API request was sent by that rejected tap.
- New handling recognizes CHECKOUT_ACKNOWLEDGED, requires the same item snapshot and requests only the delivery quote. It does not re-upload products, reset quantities or repeat preparation. A post-preparation ACTIVE cart GET is not used to prove processing state.

- Create order in CheckoutScreen invokes BuyerApp's separate confirmation, then `BrianCheckoutController.create` and `CheckoutController.create`. It requires QUOTE_READY, matching item snapshot/quote ID, unexpired valid quote and normalized phone. It reads existing owned orders, durably saves ORDER_PENDING before `POST checkout/order`, saves the numeric returned ID and verifies the exact owned order lines, totals and delivery before publishing success.
- Ambiguous order submission remains reserved. Recovery does not adopt a similar order or blindly resend. This fix does not weaken order idempotency or reconciliation safeguards.
- `orders/BuyerPayment.kt:60,83` delegates confirmed initiation to `payments/PurchaserPaymentController.kt` and lifecycle-polls authoritative status. `orders/BuyerMpesaEnvironment.kt:9` requires a verified environment for the exact API origin. UNKNOWN/empty confirmed origin blocks initiation before Retrofit.
- Request failures propagate through the shared controller's bounded code/status parsing and `state.notice` to CheckoutScreen feedback. Raw backend bodies and credentials are not presented or logged.
